## 0. Что изменено относительно исходного плана и почему

| # | Было | Стало | Причина |
|---|------|-------|---------|
| 1 | PR 1 — токены, PR 3 — TLS | PR 1 — TLS, PR 2 — токены | Bearer-токен по открытому TCP даёт перехватчику **постоянный** доступ к аккаунту. До токенов перехват даёт лишь `user_code`+`client_id`, а сервер сверяет их пару. Исходный порядок временно ухудшает безопасность |
| 2 | `Registered{auth_token}` **и** `AuthResult{ok, reason, ...}` | Один путь: `AuthOutcome::Ok / Failed(AuthError)` | Два пути возврата одних данных = двойная логика на клиенте; 4 `Option`, валидных только попарно |
| 3 | Rate limit «5/мин на IP» | Ключ `(user_code, IP)`, раздельные лимиты, TTL-зачистка | За одним NAT — десятки пользователей. В Docker при userland-proxy все клиенты могут выглядеть одним IP и лимитер положит сервис |
| 4 | Токен сохраняется в `net.rs` | Сохраняет `app.rs` | `net.rs` получает `NetCredentials` по значению в отдельный поток и не видит `AppConfig` (`app.rs:550` уже ловит `Registered`) |
| 5 | «Клиенты v2 получат VersionMismatch с понятным текстом в UI» | Старые клиенты отключаются с уже зашитым текстом; новый текст — в новом клиенте | Реакция v3 зашита в собранный бинарник (`app.rs:569`), её нельзя изменить задним числом |
| 6 | SHA-256 **с солью** | SHA-256 без соли + constant-time сравнение | Соль защищает от радужных таблиц, для 256-битного CSPRNG-токена их не существует. Критично другое — обычное `==` даёт тайминговую утечку |
| 7 | — | Обработка `UnknownAccount` | Пересоздание volume → у клиента токен несуществующего аккаунта → вечный цикл неудачной авторизации |
| 8 | — | Редактирование секретов в логах | `server/src/lib.rs:209` — `debug!("RECV: {:?}", msg)` печатает сообщение целиком |
| 9 | — | `#[serde(default)]` + тест миграции конфига | `load_config` при ошибке разбора **молча** подменяет конфиг дефолтным: потеря `user_code`, друзей, истории |
| 10 | — | Автомат состояний сессии | Сейчас `Hello` необязателен: клиент может сразу слать `Register`, обходя проверку версии |

**Уточнение к предыдущему ревью.** Ранее я предлагал вариант с challenge-response,
чтобы сохранить исходный порядок PR. Пересмотрел: по открытому TCP сейчас идут не
только учётные данные, но и **тексты сообщений, списки друзей и метаданные звонков**.
Challenge-response защищает только credential, TLS — весь канал сразу, и после него
токены становятся тривиальными. Поэтому TLS-first сильнее. Вариант с
challenge-response сохранён в Приложении А на случай, если токены нужны раньше.

## User Review Required

> [!IMPORTANT]
> **Новый TLS-порт сигналинга (PR 1)**
> - Добавляется TCP **7880** — сигналинг поверх TLS. Порт 7878 остаётся, но
>   вырождается в «порт уведомления»: отвечает старым клиентам и закрывается.
> - Self-signed сертификат генерируется сервером при первом старте в `/data`,
>   отпечаток печатается в лог; пользователь вносит его в клиент (пиннинг).
> - `docker-compose.yml` и `Dockerfile` требуют публикации нового порта.

> [!IMPORTANT]
> **Изменение протокола (PROTOCOL_VERSION: 2 → 3, PR 2)**
> - Токен аккаунта: 32 байта CSPRNG, на сервере — SHA-256 хэш, у клиента — в `config.json`.
> - До аутентификации сервер разрывает соединение на любой команде.
> - `MEDIA_VERSION` остаётся `2` вплоть до PR 4.

> [!WARNING]
> **Односторонняя совместимость**
> - TLS-рукопожатие несовместимо с plaintext-клиентом на уровне транспорта:
>   на порту 7880 старый клиент получит разрыв **без читаемой ошибки**. Именно
>   поэтому 7878 сохраняется как порт уведомления минимум на один релиз.
> - **Перед началом работ сохранить собранный бинарник клиента v3** — иначе
>   проверять совместимость будет нечем.

> [!NOTE]
> **Миграция существующих профилей**
> - Профиль без `auth_token` регистрируется и получает токен, но **только** при
>   совпадении `client_id` с записью в реестре. Каждый такой случай — в лог.
> - Путь без токена отключается после того, как аккаунт получил токен.

## 1. Дорожная карта

### Этап E2: Безопасность (текущий приоритет)

- **PR 1 (текущий)** — TLS для сигналинга: `tokio-rustls`, self-signed с
  автогенерацией, пиннинг отпечатка на клиенте, статус шифрования в UI,
  порт 7880, порт-уведомление 7878.
- **PR 2** — Аккаунты и токены: CSPRNG 32 байта, SHA-256, автомат сессии,
  `PROTOCOL_VERSION = 3`, rate-limiting, обработка `UnknownAccount`.
- **PR 3** — SQLite вместо `clients.json`: таблицы `users`, `friends`,
  `friend_requests`, `offline_messages`, идемпотентная авто-миграция с бэкапом.
- **PR 4** — Шифрование медиа: ChaCha20-Poly1305 на Opus payload,
  `MEDIA_VERSION = 3`, session key через TLS-сигналинг, заголовок 20 байт
  **остаётся открытым** (иначе релей не сможет маршрутизировать).

> Замечание к порядку PR 2 / PR 3: токены сначала лягут в `clients.json`, потом
> уедут в SQLite — формат мигрирует дважды. Либо поменять их местами, либо сразу
> проектировать `RegistryEntry` по будущей схеме `users`.

### Этап E3: Редизайн UI & UX

- Распил `ui.rs` (~68 KB) на `ui/mod.rs`, `ui/theme.rs`, `ui/screens/*`,
  `ui/widgets/*` — **отдельным коммитом с нулевым изменением поведения**.
- Дизайн-система с токенами, светлая/тёмная тема.
- Оверлей активного звонка, системные уведомления, индикатор качества связи.

### Этап E4: Аудио и групповые звонки

- RNNoise и AEC, адаптивный битрейт Opus по обратной связи о потерях.
- Групповые звонки до 6 — сначала документ «SFU vs MCU, полоса, CPU», затем код.

## 2. Детальный план PR 1 (TLS)

### Сервер

- Слушатель TLS на 7880 через `tokio-rustls` (версию подобрать совместимую с
  tokio 1.38 — зафиксировать в `workspace.dependencies`).
- Сертификат: путь из env `CHEBURGRAM_TLS_CERT` / `CHEBURGRAM_TLS_KEY`.
  Если не задан — генерация self-signed в `/data` при первом старте
  (`rcgen`), срок 10 лет, SHA-256-отпечаток в лог при каждом старте.
- Порт 7878 сохраняется: принимает соединение, отправляет
  `VersionMismatch { min: 3, max: 3 }`, закрывает. Никакой другой логики.
- `handle_client` не меняется — TLS-поток подставляется вместо `TcpStream`
  (обе половины реализуют `AsyncRead`/`AsyncWrite`, `read_frame_async` работает как есть).
- `set_nodelay` выставлять на **TCP-сокете до** TLS-обёртки.

### Клиент

- `config.rs`: `#[serde(default)] pub server_fingerprint: Option<String>`,
  `#[serde(default)] pub tls_enabled: bool`.
- `normalize_server`: порт по умолчанию 7878 → **7880**. Существующая ветка
  `":22" → ":7878"` сохраняется, но с новым портом.
- `net.rs`: TLS-коннектор с кастомным верификатором — доверять только
  закреплённому отпечатку. При первом подключении к неизвестному отпечатку —
  событие наверх, решение принимает пользователь (TOFU с явным подтверждением).
- `ui.rs`: индикатор «🔒 защищено» / «⚠ не проверено», экран подтверждения
  отпечатка, понятный текст при провале рукопожатия.

### Тесты

- Клиент с правильным отпечатком подключается; с чужим — отказ.
- Plaintext-клиент на 7880 → разрыв без паники сервера.
- Plaintext-клиент на 7878 → получает `VersionMismatch`.
- E2E из `e2e_v3.rs` переведены на TLS-транспорт, число тестов не уменьшилось.

## 3. Детальный план PR 2 (аккаунты и токены)

### 3.1. Протокол `crates/protocol/src/lib.rs`

- `PROTOCOL_VERSION: 2 → 3`. `MEDIA_VERSION` не трогать.
- Добавить:

```rust
Auth { user_code: String, token: String },
Register { client_id: String, user_code: String, name: String },
AuthOk { peer_id: u32, user_code: String, udp_port: u16, auth_token: Option<String> },
AuthFailed { error: AuthError },

pub enum AuthError {
    InvalidToken,
    UnknownAccount,
    RateLimited { retry_after_secs: u32 },
    ProtocolViolation,
}
```

- `Registered` — удалить (заменён на `AuthOk`), `AuthResult` не вводить.
- Ручной `impl Debug` для `Auth` и `AuthOk`: печатать `token: <redacted>`.
- Тесты: round-trip всех новых вариантов + `format!("{:?}", …)` не содержит токен.

### 3.2. Сервер `crates/server/src/lib.rs`

- `RegistryEntry`: `+ token_hash: Option<String>` (hex SHA-256),
  `+ token_issued_at: String`. Поле соли **не добавлять** (см. п. 6 раздела 0).
- `generate_token()` — 32 байта из `rand::rngs::OsRng` (не `thread_rng`), hex.
- `verify_token()` — constant-time сравнение (`subtle::ConstantTimeEq`).
- **Автомат сессии** вместо плоского `match`:
  `AwaitHello → AwaitAuth → Authenticated`. Сообщение не по порядку →
  `AuthFailed{ProtocolViolation}` + разрыв. Это закрывает обход проверки версии.
- `upsert` переписать на явные ветки: `новый аккаунт` / `валидный токен` /
  `грандфазеринг по client_id` / `отказ`. Ветку «выдать другой код» убрать.
- **Rate limiter**: ключ `(user_code, IP)`; на аккаунт 5/мин, на IP 60/мин;
  `SendFriendRequest` — 10/мин на аккаунт. Успешная аутентификация **сбрасывает**
  счётчик. Sliding window с TTL и зачисткой раз в минуту (иначе
  `HashMap<IpAddr, _>` — утечка и вектор DoS). Лимиты из env.
- Строка 209: заменить `debug!("RECV: {:?}", msg)` на редактированный вывод.
- Перед реализацией **проверить одной строкой лога**, какой IP реально виден
  внутри контейнера.

### 3.3. Клиент

- `config.rs`: `#[serde(default)] pub auth_token: Option<String>`.
- `net.rs` — **только транспорт**: отправить `Auth` при наличии токена, иначе
  `Register`; исход пробросить наверх как `NetEvent::Msg`.
- `app.rs` — владелец состояния: сохранить токен из `AuthOk` через `save_config`;
  на `InvalidToken` и `UnknownAccount` — **очистить токен**, перерегистрироваться,
  сохранив `display_name`, `friends`, `call_history`; на `RateLimited` — поднять
  backoff до `retry_after_secs`.
- `ui.rs`: тексты для четырёх состояний `AuthError` + баннер «сервер не знает
  вашу учётную запись, выдан новый ID».

## 5. Нерешённые вопросы (требуют явного решения до кода)

1. **Мультидевайс.** Один аккаунт = один токен, механика `SessionReplaced`
   подразумевает одну активную сессию. Значит, вход со второго устройства
   требует ручного переноса токена. Зафиксировать как принятое ограничение
   или проектировать таблицу токенов сразу в PR 3.
2. **Отзыв токена** («выйти со всех устройств») в PR 2 не предусмотрен —
   добавить `RevokeToken` или явно перенести в PR 3.
3. **`VersionMismatch { min, max }`** сейчас заполняется одинаковым значением.
   Либо поддерживать диапазон версий по-настоящему, либо упростить до одного поля.
4. **Срок жизни грандфазеринга** по `client_id` — сколько релизов держать
   путь без токена.

## Приложение А. Если токены нужны раньше TLS

Порядок PR остаётся исходным, но обычный bearer-токен заменяется на
challenge-response, чтобы секрет не ходил по открытому каналу:

- сервер после `Hello` шлёт `Challenge { nonce: [u8; 32] }` (одноразовый, TTL 30 с);
- клиент отвечает `Auth { user_code, proof }`, где
  `proof = HMAC-SHA256(sha256(token), nonce)`;
- сервер хранит `sha256(token)` и вычисляет ожидаемый `proof` — сам токен
  серверу не нужен;
- повтор перехваченного `proof` со старым nonce отклоняется.

Стоимость — один дополнительный round-trip и ~40 строк. **Важно понимать
границу**: это защищает только учётные данные. Тексты сообщений, списки друзей
и метаданные звонков останутся открытыми до появления TLS.
