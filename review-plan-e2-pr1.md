# Ревью плана Cheburgram v3 → v4 (этап E2, PR 1)

Проверено против реального кода `main` @ `f9b4e55`: `crates/server/src/lib.rs` (845 строк),
`crates/client/src/{config,net,app}.rs`, `crates/protocol/src/lib.rs`, `Dockerfile`, `docker-compose.yml`.

---

## Итоговая оценка

**План в целом верный и хорошо ложится на код.** Структура E2 → E3 → E4, разбиение
на 4 PR и состав изменений соответствуют тому, что реально есть в репозитории.
Автор плана явно читал код: `clients.json`, `ClientRegistry`, `RegistryEntry`,
`upsert`, `handle_client` названы точно, а в самом коде уже стоят заготовки —
комментарий `// Реестр клиентов (персистентный, JSON → SQLite на этапе E2)` и
`// чужой код без токена (токены — этап E2)`.

**Но есть одна блокирующая архитектурная ошибка** (токен в открытом виде до TLS)
и **три фактические неточности**, которые нужно исправить до начала работ.

Вердикт: **принять с корректировками**, перечисленными в разделах 1–2.

## 1. Блокирующее: токен ходит открытым текстом до PR 3

**Проблема.** PR 1 вводит долгоживущий bearer-токен и отправляет его по
незашифрованному TCP. TLS появляется только в PR 3. В окне между PR 1 и PR 3
любой, кто слушает трафик (Wi-Fi, транзитный провайдер, скомпрометированный
роутер), получает **постоянный** доступ к аккаунту. Сейчас, до токенов,
перехват даёт максимум `user_code` + `client_id`, а сервер хотя бы проверяет
их пару. То есть PR 1 в текущем виде **локально ухудшает** модель угроз, а не
улучшает её.

**Два допустимых решения — выбрать одно.**

**Вариант А (рекомендую) — challenge-response, порядок PR не меняется.**
Токен никогда не покидает клиента. Сервер после `Hello` шлёт случайный nonce,
клиент отвечает `HMAC-SHA256(token, nonce)`. Сервер знает токен в виде хэша —
значит, для HMAC ему нужен сам токен, поэтому хранить придётся не хэш, а
зашифрованный секрет, либо использовать схему «хэш как секрет»:
`proof = HMAC-SHA256(sha256(token), nonce)`, где на сервере лежит `sha256(token)`.
Второе проще и достаточно: перехват proof не даёт ни токена, ни возможности
переиспользования (nonce одноразовый, TTL 30 с).
Стоимость: +1 round-trip и ~40 строк кода.

**Вариант Б — поменять порядок: PR 3 (TLS) становится первым.**
TLS не зависит ни от токенов, ни от SQLite, поэтому переставляется свободно.
Тогда обычный bearer-токен безопасен. Минус: до появления токенов остаётся
дыра «угон по чужому `user_code`», но она уже частично закрыта в v3 через
сверку `client_id` в `upsert`.

Чего делать **нельзя** — оставить план как есть: bearer-токен по открытому TCP
на неопределённый срок.

## 2. Фактические неточности

### 2.1. «Клиенты v2 получат VersionMismatch с понятным текстом в UI» — невыполнимо

Старый клиент **уже собран**. Его реакция на `VersionMismatch` зашита в
`crates/client/src/app.rs:569` и никакими изменениями в v4 её не поправить.
Улучшить текст можно только в **новом** клиенте — и увидит он его в обратной
ситуации: новый клиент против старого сервера.

Формулировку заменить на: «старые клиенты будут корректно отключены с уже
существующим сообщением; понятный текст добавляется в новый клиент для случая
подключения к устаревшему серверу».

Отдельно учесть: супервизор в `net.rs` переподключается вечно с backoff до 30 с.
Все старые клиенты превратятся в фоновый поток реконнектов раз в 30 с. Само по
себе безобидно, но это надо развести с новым rate-limiter'ом (см. 2.3), иначе
они забьют его счётчики.

### 2.2. Сохранение токена — в `app.rs`, а не в `net.rs`

План указывает `net.rs` как место сохранения токена. Это не сойдётся с кодом:
`net.rs` получает `NetCredentials` **по значению** в отдельный поток и не имеет
доступа к `AppConfig`; конфигом владеет `app.rs`, который уже обрабатывает
`ControlMessage::Registered` на строке `app.rs:550`.

Правильное разделение:
- `net.rs` — только транспорт: отправить `Auth`/`Register`, пробросить ответ
  наверх как `NetEvent::Msg(...)`;
- `app.rs` — принять токен, положить в `AppConfig`, вызвать `save_config`;
- `config.rs` — поле `auth_token: Option<String>` (плюс `#[serde(default)]`,
  иначе старые `config.json` перестанут парситься — в `load_config` при ошибке
  разбора конфиг **молча заменяется на дефолтный**, то есть пользователь
  потеряет `user_code`, список друзей и историю звонков).

Последнее — реальный риск потери данных, его в плане нет.

### 2.3. Rate limiting по IP — неверная гранулярность

Три отдельные проблемы:

1. **NAT.** Офис, общежитие, мобильный оператор — десятки легитимных
   пользователей за одним IP. Лимит «5 попыток/мин на IP» заблокирует всех.
2. **Docker.** Прежде чем ключевать по IP, проверьте, какой адрес реально
   виден внутри контейнера. При iptables-DNAT исходный IP сохраняется, но при
   включённом userland-proxy соединения могут приходить с адреса шлюза —
   тогда **все** клиенты выглядят как один IP и лимитер положит сервис
   целиком. Проверяется одной строкой лога в `handle_client`.
3. **Неограниченный рост.** `HashMap<IpAddr, Counter>` без вытеснения — это
   утечка памяти и вектор DoS: атакующий с ботнета раздувает таблицу.

Корректная схема:
- ключ — **пара** `(user_code, IP)`, лимиты раздельные: на аккаунт строже
  (5/мин), на IP мягче (60/мин) — IP-лимит защищает от перебора кодов, а не
  от нескольких человек за NAT;
- **успешная** аутентификация по валидному токену сбрасывает счётчик и не
  штрафуется — иначе реконнекты при плохой сети сами себя заблокируют;
- окно — sliding window с TTL и периодической зачисткой (раз в минуту), либо
  фиксированный размер LRU;
- ответ при срабатывании — машиночитаемый `RateLimited { retry_after_secs }`,
  чтобы клиент увеличил backoff, а не долбил дальше.

### 2.4. SHA-256 вместо argon2 — план прав, моя прошлая рекомендация была неточна

В предыдущем промте я предлагал «argon2/sha256+salt». Для этого случая
**argon2 не нужен и вреден**: токен — 32 байта из CSPRNG, энтропия 256 бит,
перебор невозможен в принципе. Медленный KDF здесь только добавит задержку на
каждое подключение и станет вектором DoS. `SHA-256` — правильный выбор.

Два уточнения к нему:
- соль для высокоэнтропийного токена не нужна (она защищает от радужных
  таблиц, а их для 256-битного случайного значения не существует); оставить
  можно, вреда нет, но и поля `token_salt` можно избежать;
- сравнение хэшей **обязательно constant-time** (`subtle::ConstantTimeEq` или
  ручное `fold`-сравнение). Обычное `==` на строках даёт таймингову утечку.

## 3. Пробелы, которых в плане нет

### 3.1. Потеря данных сервера → «осиротевший» токен

Сценарий: volume `cheburgram-data` пересоздан, БД пуста. У клиента лежит токен
для `user_code`, которого больше не существует. План этот случай не описывает,
а произойдёт он обязательно — при переезде на VPS или откате контейнера.

Решение: сервер отвечает `UnknownAccount`; клиент **очищает** токен, повторно
регистрируется, сохраняя `display_name` и список друзей, и показывает
предупреждение «сервер не знает вашу учётную запись, выдан новый ID». Без
этого клиент уйдёт в вечный цикл неудачной авторизации.

### 3.2. Окно «дедовщины» при миграции

Существующие пользователи токенов не имеют. Первое подключение выдаёт токен —
и тот, кто успел первым, забирает аккаунт. Привязка к `client_id` (как в
текущем `upsert`) закрывает основную часть риска, но `client_id` — это просто
UUID из `config.json`, он никогда не проверялся и не является секретом.

Мягкая мера: грандфазеринг разрешать **только** при совпадении `client_id`,
писать в лог каждое такое событие, а через N дней (или после первой выдачи
токена аккаунту) отключать путь без токена совсем.

### 3.3. `Hello` не является обязательным — проверку версии можно обойти

В `handle_client` сообщения разбираются простым `match` в цикле; клиент,
который **не** прислал `Hello`, спокойно доходит до `Register`. Проверка
версии обходится тривиально. Раз уж вводится состояние сессии, нужен
полноценный автомат: `ожидание Hello → ожидание Auth/Register → авторизован`,
и любое сообщение не по порядку — разрыв соединения.

### 3.4. Токен утечёт в логи

`crates/server/src/lib.rs:209` — `debug!("RECV: {:?}", msg);` печатает **всё**
сообщение целиком. С `RUST_LOG=debug` токены окажутся в логах Docker в
открытом виде. Нужен ручной `Display`/редактирование для `Auth`, `Register`,
`Registered`, `AuthResult` — печатать `token: <redacted>`. То же самое на
клиенте.

### 3.5. Мультидевайс не определён

Один аккаунт = один токен. Что происходит при входе со второго устройства?
Механика `SessionReplaced` уже подразумевает «одна активная сессия», значит
токен должен быть **на аккаунт**, а не на устройство, и его придётся
переносить руками. Это допустимое решение, но его надо зафиксировать явно —
иначе на этапе реализации всплывёт как сюрприз. Заодно: отзыв токена
(«выйти со всех устройств») в PR 1 не предусмотрен — либо добавить
`RevokeToken`, либо честно записать в PR 2.

### 3.6. `AuthResult` со строковым `reason` — плохой контракт

`AuthResult { ok: bool, reason: Option<String>, peer_id: Option<u32>, ... }`
заставляет клиента сопоставлять строки, чтобы различить «неверный токен →
очистить и перерегистрироваться», «rate limit → увеличить backoff» и
«аккаунт неизвестен → новый ID». Четыре `Option`, валидные только попарно, —
это состояние, которое можно собрать неправильно.

Лучше типизировать:

```rust
pub enum AuthOutcome {
    Ok { peer_id: u32, user_code: String, udp_port: u16, auth_token: Option<String> },
    Failed(AuthError),
}

pub enum AuthError {
    InvalidToken,
    UnknownAccount,
    RateLimited { retry_after_secs: u32 },
    ProtocolViolation,
}
```

И тогда **не нужен** `auth_token: Option<String>` в `Registered` — два разных
пути возврата одних и тех же данных (`Registered` и `AuthResult`) порождают
двойную логику на клиенте. Оставить один путь: `AuthOutcome::Ok`.

### 3.7. Порядок PR 1 / PR 2 создаёт лишнюю работу

Токены сначала пишутся в `clients.json`, а через PR уезжают в SQLite —
формат хранения токенов придётся мигрировать дважды. Либо поменять PR 1 и
PR 2 местами, либо сразу проектировать `RegistryEntry` по будущей схеме
таблицы `users`, чтобы миграция была механической.

## 4. Мелочи

- `PROTOCOL_VERSION` и `MEDIA_VERSION` независимы: PR 1 трогает только первую,
  `MEDIA_VERSION` остаётся `2` до PR 4. В плане это не сказано явно.
- `VersionMismatch { min, max }` сервер сейчас заполняет одинаковым значением.
  Если планируется поддержка диапазона версий — надо решить сейчас; если нет —
  упростить до одного поля.
- В `Dockerfile` `VOLUME ["/data"]` и `WORKDIR /data`, а `CLIENTS_FILE` —
  относительный путь `"clients.json"`. Для SQLite в PR 2 путь лучше вынести в
  переменную окружения, а не полагаться на рабочую директорию.
- Формулировка «не более 5 попыток/мин на IP» в плане приведена как
  окончательная — числа стоит сделать конфигурируемыми через env.

## 5. Скорректированная спецификация PR 1

### Протокол (`crates/protocol/src/lib.rs`)

- `PROTOCOL_VERSION: 2 → 3`; `MEDIA_VERSION` не трогать.
- Добавить:
  - `Challenge { nonce: [u8; 32] }` — ответ сервера на `Hello` (вариант А);
  - `Auth { user_code: String, proof: [u8; 32] }` — `HMAC-SHA256(sha256(token), nonce)`;
  - `Register { client_id, user_code, name, proof: Option<[u8;32]> }` — первичный вход;
  - `AuthOutcome` / `AuthError` вместо `AuthResult` и `Registered.auth_token`.
- Round-trip тесты на все новые варианты + тест, что `Debug` не печатает токен.

### Сервер (`crates/server/src/lib.rs`)

- `RegistryEntry`: `+ token_hash: Option<String>` (hex sha256), `+ token_issued_at: String`.
  Соль опциональна — обосновать решение в PR.
- `generate_token()` — 32 байта CSPRNG (`rand::rngs::OsRng`, не `thread_rng`).
- `verify_proof(user_code, nonce, proof) -> bool` — constant-time сравнение.
- Автомат сессии: `Hello → Challenge → Auth|Register → Authenticated`.
  Всё вне порядка — разрыв, а не `Error`.
- До аутентификации любая команда → `AuthError::ProtocolViolation` + разрыв.
- Rate limiter по `(user_code, IP)` с TTL-зачисткой, лимиты из env, сброс
  счётчика при успехе.
- Редактирование секретов в `debug!` на строке 209.
- `upsert` переписать: убрать «выдать другой код», развести на явные ветки
  `новый аккаунт` / `валидный токен` / `грандфазеринг по client_id` / `отказ`.

### Клиент

- `config.rs`: `#[serde(default)] pub auth_token: Option<String>`;
  тест, что старый `config.json` **без** поля парсится и не теряет `user_code`,
  `friends`, `call_history`.
- `net.rs`: только транспорт — ответить на `Challenge`, отправить `Auth`
  или `Register`, пробросить исход наверх.
- `app.rs`: сохранение токена, обработка `AuthError` — очистка токена при
  `InvalidToken`/`UnknownAccount`, увеличение backoff при `RateLimited`.
- `ui.rs`: тексты для четырёх состояний ошибки + индикация «требуется
  повторная регистрация».

## 6. Дополнения к плану верификации

К автоматическим тестам добавить:

- старый `config.json` без `auth_token` → парсится, данные целы;
- сервер с пустым реестром + клиент с токеном → `UnknownAccount`, клиент
  восстанавливается, а не зацикливается;
- повторное использование перехваченного `proof` со **старым** nonce → отказ;
- rate limiter: 6 неудач подряд → блок; успешный вход → счётчик сброшен;
- два клиента за одним IP → второй **не** блокируется из-за первого;
- команда до аутентификации (`CallRequest`, `SendTextMessage`) → разрыв;
- `Register` без предшествующего `Hello` → разрыв;
- `format!("{:?}", ControlMessage::Auth{..})` не содержит токен;
- rate-limiter не растёт по памяти на 10 000 уникальных IP (зачистка работает).

К ручной проверке добавить:

- клиент v3 (собранный бинарник **сохранить заранее**, иначе проверять будет
  нечем) против сервера v4 → корректное отключение, без зависания;
- обрыв сети на 60 с во время звонка → реконнект проходит авторизацию
  автоматически, звонок восстанавливается или корректно завершается;
- пересоздание Docker-volume → сценарий 3.1 отрабатывает;
- `RUST_LOG=debug` на сервере → в логах нет ни одного токена.
